# Документ требований

## Введение

Данный документ описывает требования к клиентской части интернет-ресурса для размещения объявлений о продаже подержанных вещей. Проект выполняется в рамках курсовой работы по дисциплине «Фронтенд-разработка» согласно нормативному документу СМКО МИРЭА 7.5.1/04.11.05-18.

Клиентская часть реализуется на HTML5, CSS3 и JavaScript (ES6+) с использованием сборщика Vite, методологии вёрстки БЭМ, адаптивного дизайна и объектно-ориентированного подхода в JavaScript. Приложение интегрируется с внешними API и публикуется на GitHub Pages.

---

## Глоссарий

- **Marketplace** — клиентская часть интернет-ресурса для размещения объявлений о продаже подержанных вещей.
- **Listing** — объявление о продаже подержанного товара, содержащее заголовок, описание, цену, категорию и изображение.
- **Listing_Card** — визуальный компонент, отображающий краткую информацию об одном объявлении в виде карточки.
- **Listing_Detail** — страница или модальное окно с полной информацией об объявлении.
- **Catalog** — страница со списком всех доступных объявлений с возможностью фильтрации и поиска.
- **Search_Bar** — компонент строки поиска объявлений по ключевым словам.
- **Filter_Panel** — компонент панели фильтрации объявлений по категории, цене и другим параметрам.
- **Create_Form** — форма создания нового объявления.
- **API_Client** — JavaScript-класс, инкапсулирующий логику взаимодействия с внешними API.
- **Geo_API** — внешний API для получения данных о местоположении (например, DaData или аналог).
- **Currency_API** — внешний API для получения актуальных курсов валют.
- **Router** — клиентский маршрутизатор, управляющий навигацией между страницами без перезагрузки.
- **User** — посетитель сайта, просматривающий или размещающий объявления.
- **BEM** — методология именования CSS-классов (Блок, Элемент, Модификатор).
- **Breakpoint** — контрольная точка ширины экрана для адаптивной вёрстки.

## Требования

### Требование 1: Главная страница и навигация

**User Story:** Как пользователь, я хочу видеть главную страницу с навигацией, чтобы быстро ориентироваться в разделах сайта и переходить к нужному контенту.

#### Критерии приёмки

1. THE Marketplace SHALL отображать главную страницу с шапкой (header), содержащей логотип, навигационное меню (не более 10 пунктов) и кнопку размещения объявления.
2. THE Router SHALL обеспечивать навигацию между страницами без полной перезагрузки браузера с использованием History API.
3. WHEN пользователь нажимает на пункт навигационного меню, THE Router SHALL обновлять отображаемый контент и URL в адресной строке без перезагрузки страницы, а активный пункт меню SHALL получать визуальное выделение (CSS-класс `nav__item--active`).
4. WHILE страница загружается, THE Marketplace SHALL отображать индикатор загрузки на месте основного контента; WHEN загрузка завершается, THE Marketplace SHALL скрывать индикатор и отображать контент.
5. IF загрузка страницы превышает 10 секунд, THEN THE Marketplace SHALL скрывать индикатор загрузки и отображать сообщение «Не удалось загрузить страницу. Попробуйте обновить.» с кнопкой повторной загрузки.
6. IF запрошенный маршрут не существует, THEN THE Router SHALL отображать страницу с сообщением «Страница не найдена» и ссылкой на главную страницу, сохраняя запрошенный URL в адресной строке.
7. THE Marketplace SHALL отображать подвал (footer) с информацией об авторе курсовой работы, годом создания и ссылкой на репозиторий GitHub.

### Требование 2: Каталог объявлений

**User Story:** Как пользователь, я хочу просматривать список объявлений о продаже подержанных вещей, чтобы найти интересующий меня товар.

#### Критерии приёмки

1. THE Catalog SHALL отображать список объявлений в виде сетки карточек (Listing_Card).
2. WHEN страница каталога открывается, THE Catalog SHALL отображать индикатор загрузки, а THE API_Client SHALL загружать данные объявлений из внешнего источника (JSON-файл или REST API) и передавать их компоненту Catalog.
3. THE Listing_Card SHALL отображать изображение товара, заголовок объявления, цену, категорию и дату публикации; IF изображение товара недоступно, THEN THE Listing_Card SHALL отображать изображение-заглушку.
4. WHEN данные объявлений успешно загружены, THE Catalog SHALL скрывать индикатор загрузки и отрисовывать все полученные Listing_Card без дублирования.
5. IF загрузка данных завершается ошибкой, THEN THE Catalog SHALL скрывать индикатор загрузки и отображать сообщение «Не удалось загрузить объявления» с кнопкой «Попробовать снова».
6. THE Catalog SHALL отображать не более 20 объявлений на одной странице с элементами пагинации (кнопки «Предыдущая» / «Следующая» и номера страниц).
7. WHEN количество объявлений превышает 20, THE Catalog SHALL отображать элементы пагинации; WHEN пользователь нажимает на номер страницы или кнопку навигации, THE Catalog SHALL отображать соответствующую страницу объявлений.

---

### Требование 3: Поиск и фильтрация объявлений

**User Story:** Как пользователь, я хочу искать и фильтровать объявления, чтобы быстро находить товары по нужным критериям.

#### Критерии приёмки

1. THE Search_Bar SHALL принимать текстовый ввод пользователя и фильтровать список объявлений по совпадению с заголовком или описанием без учёта регистра символов.
2. WHEN пользователь вводит текст в Search_Bar, THE Catalog SHALL обновлять отображаемый список объявлений не позднее чем через 300 мс после последнего нажатия клавиши (debounce) без перезагрузки страницы.
3. THE Filter_Panel SHALL предоставлять элементы управления для фильтрации объявлений по категории товара и диапазону цены; диапазон цены SHALL принимать значения от 0 до 10 000 000 рублей включительно.
4. WHEN пользователь применяет фильтр в Filter_Panel, THE Catalog SHALL отображать только объявления, соответствующие всем выбранным критериям одновременно (логика AND).
5. WHEN пользователь очищает все фильтры, THE Catalog SHALL отображать полный список объявлений.
6. IF поиск или фильтрация не возвращают ни одного объявления, THEN THE Catalog SHALL отображать сообщение «Объявления не найдены» вместо пустой сетки.
7. THE Filter_Panel SHALL поддерживать одновременное применение нескольких фильтров (категория и диапазон цены), объединяя их по логике AND.

### Требование 4: Страница детального просмотра объявления

**User Story:** Как пользователь, я хочу просматривать полную информацию об объявлении, чтобы принять решение о покупке.

#### Критерии приёмки

1. WHEN пользователь нажимает на Listing_Card, THE Router SHALL переходить на страницу Listing_Detail соответствующего объявления.
2. THE Listing_Detail SHALL отображать изображение товара, заголовок, полное описание, цену, категорию, дату публикации в формате ДД.ММ.ГГГГ, имя продавца и способ связи с ним.
3. WHEN страница Listing_Detail открывается, THE Listing_Detail SHALL отображать индикатор загрузки, а THE API_Client SHALL загружать полные данные объявления по его идентификатору; WHEN данные получены, THE Listing_Detail SHALL скрывать индикатор и отображать все поля объявления.
4. IF данные объявления не найдены по указанному идентификатору, THEN THE Listing_Detail SHALL отображать сообщение «Объявление не найдено» и ссылку на каталог.
5. IF загрузка данных объявления завершается сетевой ошибкой (не 404), THEN THE Listing_Detail SHALL отображать сообщение «Не удалось загрузить объявление» с кнопкой «Попробовать снова».
6. THE Listing_Detail SHALL отображать кнопку «Назад к каталогу»; WHEN пользователь нажимает на неё, THE Router SHALL возвращать пользователя на страницу каталога с восстановленными параметрами фильтрации и поиска, активными до перехода на страницу объявления.

---

### Требование 5: Форма создания объявления

**User Story:** Как пользователь, я хочу размещать объявления о продаже подержанных вещей, чтобы найти покупателей.

#### Критерии приёмки

1. THE Create_Form SHALL содержать обязательные поля: заголовок объявления (5–100 символов), описание (до 2000 символов), цена (0–10 000 000 рублей), категория (выбор из списка) и необязательное поле изображения (URL или загрузка файла).
2. WHEN пользователь отправляет Create_Form, THE Create_Form SHALL валидировать все обязательные поля перед сохранением данных.
3. IF обязательное поле не заполнено при отправке формы, THEN THE Create_Form SHALL отображать сообщение об ошибке рядом с соответствующим полем без перезагрузки страницы.
4. IF введённая цена содержит нечисловые символы, отрицательное значение или превышает 10 000 000, THEN THE Create_Form SHALL отображать сообщение «Введите корректную цену (от 0 до 10 000 000)» рядом с полем цены.
5. IF заголовок объявления содержит менее 5 или более 100 символов, THEN THE Create_Form SHALL отображать сообщение «Заголовок должен содержать от 5 до 100 символов» рядом с полем заголовка.
6. WHEN все поля формы заполнены корректно и пользователь нажимает кнопку отправки, THE Create_Form SHALL добавлять новое объявление в локальное хранилище (localStorage), очищать сохранённый черновик и перенаправлять пользователя на страницу каталога.
7. WHILE пользователь заполняет Create_Form, THE Create_Form SHALL сохранять введённые данные в localStorage при каждом изменении поля, чтобы пользователь не терял незавершённый черновик при переходе между страницами.

### Требование 6: Адаптивная вёрстка

**User Story:** Как пользователь, я хочу комфортно пользоваться сайтом на любом устройстве, чтобы просматривать объявления с телефона, планшета или компьютера.

#### Критерии приёмки

1. THE Marketplace SHALL корректно отображаться на экранах с шириной от 320px до 1920px без горизонтальной прокрутки.
2. WHEN ширина экрана составляет менее 768px (мобильный Breakpoint), THE Marketplace SHALL отображать каталог в виде одноколоночной сетки карточек.
3. WHEN ширина экрана составляет от 768px до 1199px (планшетный Breakpoint), THE Marketplace SHALL отображать каталог в виде двухколоночной сетки карточек.
4. WHEN ширина экрана составляет 1200px и более (десктопный Breakpoint), THE Marketplace SHALL отображать каталог в виде сетки из трёх или четырёх колонок карточек.
5. WHEN ширина экрана составляет менее 768px, THE Marketplace SHALL заменять горизонтальное навигационное меню на иконку «гамбургер»; WHEN пользователь нажимает на иконку, THE Marketplace SHALL отображать выпадающее меню со всеми пунктами навигации.
6. THE Marketplace SHALL использовать относительные единицы измерения (rem, %, vw) для шрифтов и отступов, чтобы обеспечить масштабируемость интерфейса.
7. THE Marketplace SHALL применять CSS-методологию BEM для именования всех CSS-классов без исключений: каждый класс SHALL соответствовать шаблону `блок`, `блок__элемент` или `блок--модификатор`.

### Требование 7: Интеграция внешних API

**User Story:** Как пользователь, я хочу видеть актуальные данные из внешних источников, чтобы получать дополнительную полезную информацию при просмотре объявлений.

#### Критерии приёмки

1. THE API_Client SHALL предоставлять методы fetchListings(), fetchListingById(id), fetchCurrencyRates() и fetchGeoSuggestions(query) другим компонентам приложения через публичный интерфейс класса.
2. WHEN страница Listing_Detail открывается, THE API_Client SHALL запрашивать актуальные курсы валют у Currency_API и THE Listing_Detail SHALL отображать цену объявления одновременно в рублях (RUB), долларах США (USD) и евро (EUR).
3. IF запрос к Currency_API завершается ошибкой или превышает время ожидания 5 секунд, THEN THE Listing_Detail SHALL отображать только цену в рублях без конвертации, остальные данные объявления SHALL оставаться доступными, а THE API_Client SHALL записывать сообщение об ошибке в консоль браузера.
4. WHEN пользователь вводит не менее 3 символов в поле города формы Create_Form, THE API_Client SHALL запрашивать подсказки адресов у Geo_API и THE Create_Form SHALL отображать выпадающий список вариантов.
5. IF запрос к Geo_API завершается ошибкой, THEN THE Create_Form SHALL скрывать выпадающий список подсказок, сохранять уже введённый пользователем текст в поле города и позволять пользователю продолжать ввод вручную.
6. THE API_Client SHALL кэшировать результаты запросов к Currency_API в sessionStorage на время сессии, чтобы не выполнять повторные запросы при каждом открытии Listing_Detail.

### Требование 8: Объектно-ориентированная архитектура JavaScript

**User Story:** Как разработчик, я хочу использовать ООП при написании JavaScript-кода, чтобы обеспечить модульность, читаемость и расширяемость приложения.

#### Критерии приёмки

1. THE Marketplace SHALL реализовывать каждый UI-компонент (Catalog, Listing_Card, Listing_Detail, Create_Form, Search_Bar, Filter_Panel) как отдельный JavaScript-класс, где метод render() возвращает или вставляет DOM-узел компонента, метод init() навешивает обработчики событий, а метод destroy() удаляет обработчики событий и DOM-узел компонента.
2. WHEN метод destroy() компонента вызван, THE компонент SHALL прекращать реагировать на любые пользовательские события и DOM-события.
3. THE API_Client SHALL реализовывать методы fetchListings(), fetchListingById(id), fetchCurrencyRates() и fetchGeoSuggestions(query) как методы класса; IF любой из методов завершается ошибкой, THEN метод SHALL выбрасывать исключение с описательным сообщением.
4. THE Router SHALL реализовываться как JavaScript-класс с методами navigate(path), registerRoute(path, handler) и handlePopState(); IF пользователь переходит по незарегистрированному маршруту, THEN THE Router SHALL вызывать обработчик 404-страницы.
5. THE Marketplace SHALL использовать ES6-модули (import/export) для организации кода по файлам, где каждый класс располагается в отдельном файле.

### Требование 9: Сборка и публикация на GitHub Pages

**User Story:** Как разработчик, я хочу собирать и публиковать проект на GitHub Pages, чтобы предоставить доступ к работающему приложению по публичному URL.

#### Критерии приёмки

1. THE Marketplace SHALL собираться с помощью Vite, формируя оптимизированный набор статических файлов в директории dist/.
2. WHEN выполняется команда npm run build, THE Marketplace SHALL успешно завершать сборку без ошибок и предупреждений ESLint.
3. THE Marketplace SHALL публиковаться на GitHub Pages из ветки gh-pages или директории docs/ с использованием пакета gh-pages или GitHub Actions.
4. WHEN опубликованное приложение открывается по URL вида https://{username}.github.io/{repository}/, THE Marketplace SHALL корректно загружаться и отображать главную страницу.
5. IF базовый путь (base path) приложения отличается от корневого, THEN конфигурация Vite SHALL содержать параметр base, соответствующий пути репозитория на GitHub Pages.
6. THE Marketplace SHALL содержать файл README.md с описанием проекта, инструкцией по локальному запуску и ссылкой на опубликованное приложение.

### Требование 10: Качество кода и инструменты разработки

**User Story:** Как разработчик, я хочу поддерживать высокое качество кода с помощью инструментов статического анализа и форматирования, чтобы соответствовать стандартам курсовой работы.

#### Критерии приёмки

1. THE Marketplace SHALL содержать конфигурационный файл ESLint (.eslintrc или eslint.config.js), настроенный для ES6+ и браузерного окружения.
2. THE Marketplace SHALL содержать конфигурационный файл Prettier (.prettierrc), определяющий единый стиль форматирования кода.
3. WHEN разработчик выполняет команду npm run lint, THE Marketplace SHALL завершать проверку без ошибок ESLint.
4. WHEN разработчик выполняет команду npm run format, THE Marketplace SHALL форматировать все файлы проекта согласно конфигурации Prettier без ошибок.
5. THE Marketplace SHALL использовать Git для контроля версий; каждое сообщение коммита SHALL содержать осмысленное описание изменений (не допускаются сообщения вида «fix», «update», «changes» без уточнения).
6. THE Marketplace SHALL содержать файл .gitignore, исключающий директории node_modules/ и dist/ из репозитория.
